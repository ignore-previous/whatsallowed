## 1. What was built and how

What's Allowed (npm `whatsallowed`) is a command-line tool. You run it in a project folder. It reads Claude Code, Codex and Cursor config files and flags risky settings. Each flag has a rule ID, a file and line, a reason and a fix. There are 10 checks and 35 rules. It also has a Claude Code plugin wrapper, a SARIF output for GitHub, and a baseline feature that spots changed MCP servers.

It was built mainly by Claude Opus 5.5 over several overnight runs. Claude helper agents wrote the labelled test cases. A Claude Sonnet 5.5 model and GPT-6 (Codex) labelled the real-world alerts. The package ships one bundled file, two parser libraries inside it, and three docs. The repo has 391 tracked files.

## 3. What had no human expert check

This is the part that matters most. **No human has checked any label or any rule.**

- Every test case (dev, test, Windows) was written and labelled by Claude agents. The checks were written by Claude Opus 5.5 and tuned on cases the same agent wrote. The held-out set was written by other helper agents, but they are the same model family and read the same labelling rule.
- The 30-case blind labelling in `launch/README.md` step 3 was **not done**. `eval/kappa/reviewer-labels.json` does not exist, only the empty template. `docs/ACCURACY.md` line 111 says so plainly. The "kappa 1.00" figure is about two models agreeing on real-world alerts. It is not a measure of the test set and it is not a human check.
- The 92 real-world alerts: both labellers are models. One is Claude Sonnet 5.5, my own family. That is a conflict of interest, and the reason GPT-6 was added. They agreed on every alert, which is reassuring but also what you would expect if both share the same blind spots.
- The 20 masked alerts in the private spot-check list are **not answered yet**. They are the only planned human check.
- Secret alerts were labelled from masked output only. Nobody opened a value, so the 9 secret alerts are "looks like a key" judgements, not confirmed live keys.
- No security professional has reviewed the rule set, the threat model or the severity levels. Whether a given setting is "high" or "medium" is a product judgement made by models.
- Vendor behaviour (what Claude Code, Codex and Cursor really do with each setting) comes from the vendors' docs as read by a model (`docs/config-surface.md`). Nothing was tested against the live tools.

## 5. Known limits and failure modes

What it doesn't do is stated well in the README and `docs/THREAT_MODEL.md`: no run-time view of MCP servers, no reading of prose for prompt injection, no following of hooks into local scripts, no Cursor run-mode, nothing set by an administrator.

Things I found that the docs don't fully say:

1. **A high false alarm on a real installed plugin.** I ran `--user-only` on this machine. It flagged Anthropic's official `security-guidance` plugin (`hooks/llm.py:1137`) as HIGH `SKILL-001`, "downloads code and runs it". That line is a paragraph of English instructions inside a string, not code. The fix text says "Remove the skill or plugin". Anyone with that plugin installed will see this on their first run. No test case or real-world sample covers it, because the real-world run fetched only three config files.
2. **Clean-looking output when nothing was checked.** Run in an empty folder, it prints "checked 0 config files. No high or medium findings." and exits 0. That reads like a pass. It should say there was nothing to check.
3. **Double alerts.** MODE-005 and MODE-006 both fired on the same file in 3 of 4 repos. One setting raises two alerts.
4. **Headline 100% table.** The main table in `ACCURACY.md` is the score after fixing the cases the first run missed (DENY recall was 90% and SKILL recall 80% on first run). This is disclosed in the history section. But the top table is the one people will quote.
5. **Small samples.** About 10 risky cases per check. One case moves a figure by about 10 points.
6. **Sample bias.** The real-world sample is GitHub search results, not random, and overlaps an earlier 19 Oct sample.
7. **Obfuscation.** A person trying to hide a download-and-run can. The docs say so.
8. **Brand collision risk is low.** The brand check found no scanner treats the name as injection.

Overclaims (where a non-expert could get a false sense of safety or accuracy):

- `README.md:87`: "measured on a held-out test set that was written and frozen before tuning". True for the first run only. The cases that failed were then fixed for, so those figures are no longer on unseen cases. `ACCURACY.md:48-54` says this; the README doesn't.
- `README.md:7`: "Every check publishes its precision and recall". Recall exists only on synthetic cases. The README doesn't say real-world recall is unknown or that all labels come from models. A reader will assume expert-checked.
- `docs/ACCURACY.md:128` and `:132`: "Known misses: None" and "False alarms: None". Literally true for the synthetic test split, but the real-world section above shows two false alarms. A reader skimming headings gets the wrong picture. Add a pointer to the real-world section.
- `launch/show-hn.md:13`: "labelled every alert by hand". The labelling was by models. This must change before posting.
- `launch/show-hn.md:13` and `launch/reddit.md:21`: "held-out ... frozen before I tuned anything". Same issue as the README line above.
- `README.md:5`: "a test proves". Say "a test checks".

"A configuration check, not a security assessment" is said clearly enough. It is in the README (line 9, early), the tool's own final line, `ACCURACY.md`, `checks.md`, the threat model and `SECURITY.md`. The plugin skill tells Claude to repeat it on a clean result. I would move the README sentence up to sit directly under the first paragraph so it is read before the accuracy claim.

## 6. Worst realistic outcome

- **False sense of safety (most likely harm).** Someone runs it, sees "No high or medium findings" and relaxes, while a risk it can't see (a script a hook calls, a malicious MCP server, prompt injection in a file) is still there. The wording mitigates this but doesn't remove it. Misleading output on an empty folder makes it worse.
- **False alarms (most likely embarrassment).** A HIGH on a well-known plugin, or on `node --version`, in a public post. Expect one or two comments of this kind in the first week. It's the most likely thing to dent trust in the "published accuracy" pitch, because the pitch invites people to check.
- **Accuracy challenged.** Someone points out that the labels are all from models, or that the "held-out" set was fixed after its first run. The tool does disclose both, but the posts don't yet. This is the realistic reputation risk for the owner.
- **Privacy or security problem in the tool itself.** Unlikely. No network, no telemetry, one owner-only file write, secrets masked in all outputs. A bug in a path-handling or parsing step is possible but would most likely crash the tool, not leak data. Output does include file paths in the home folder, which the docs warn about.
- **Repo history.** The plan to publish a single fresh commit avoids the known history problems (a local user name in an early commit, progress notes, whole fake keys). I did not run the export steps.

## 8. Recommendation

The weak points are wording and one visible false alarm, and all of them are cheap to fix. None of the problems I found needs a redesign.
