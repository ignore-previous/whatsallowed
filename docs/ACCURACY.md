Two kinds of figure are reported, and they answer different questions:

- **Spec conformance (synthetic, frozen)**: does each check flag what the labelling rule says it should, on hand-written cases it wasn't tuned on? This gives precision and recall.
- **Real-world precision (sampled public configs, dated)**: when a check fires on configs people actually commit, how often is the alert right? This gives precision only.

## Real-world precision (sampled public configs, dated)

Run on 2026-10-22 with whatsallowed in project-only mode, on 110 public repositories (64 `.claude/settings.json`, 52 `.mcp.json`, 32 `.codex/config.toml`). GitHub code search for each of the three files at a project root (up to the first 300 results per file, forks and the maintainer's own repositories left out), then a seeded random draw from the results (seed 20261022), with each of the three files fetched from every drawn repository. Only those config files were read. 31 of the 110 repositories had at least one alert. Every high or medium alert was labelled against [LABELLING.md](../eval/LABELLING.md) by two models working blind, from a masked copy of each alert: Claude Sonnet 5.5 and GPT-6 (Codex). They agreed on all 92 (Cohen's kappa 1.00), and a third model (Claude Opus 5.5) reviewed the alerts either was unsure about. Secret alerts were labelled from the masked output only. Every label came from a model; no person labelled any alert. Only these totals are published: no repository, owner or file is named, and no third-party file is kept (`eval/realworld/2026-10-22.json`).

This measures precision only (how many alerts were right). It can't measure recall, because nobody knows how many risky settings the sample holds. "Low value" counts alerts that are right by the rule's wording but look harmless in context; they are included in "Correct".

|---|---|---|---|---|---|
| `MODE` | 9 | 9 | 0 | 0 | 100% (70%–100%) |
| `ALLOW` | 20 | 19 | 1 | 0 | 95% (76%–99%) |
| `DENY` | 0 | 0 | 0 | 0 | no alerts |
| `ENDPOINT` | 2 | 1 | 1 | 1 | 50% (9%–91%) |
| `HOOK` | 0 | 0 | 0 | 0 | no alerts |
| `HTTPHOOK` | 0 | 0 | 0 | 0 | no alerts |
| `MCP` | 52 | 52 | 0 | 1 | 100% (93%–100%) |
| `DRIFT` | 0 | 0 | 0 | 0 | no alerts |
| `SECRET` | 9 | 9 | 0 | 0 | 100% (70%–100%) |
| `SKILL` | 0 | 0 | 0 | 0 | no alerts |

- Two alerts were wrong: an allow rule for `node --version` alone (ALLOW), and `AWS_PROFILE` set to the placeholder `your-profile-here` (ENDPOINT).
- Two more are right only by the rule's wording and look harmless in context: a repository `awsAuthRefresh` command that logs into a placeholder profile (ENDPOINT), and a plain `sh -c "cd … && exec …"` launch (MCP). They are candidates for narrowing the rules, not counted as false alarms.
- In three of the four repositories where MODE-006 fired, MODE-005 fired on the same file too, so one setting raised two alerts.
- Only config files were fetched, so DENY (needs a secrets file), SKILL (needs scripts) and DRIFT (needs a baseline) can't fire here. HOOK and HTTPHOOK could fire but raised no alerts in this sample.
- Search results are ranked by GitHub, not random, and repositories that commit these files may differ from those that keep them local. This sample may share repositories with the 19 Oct 2026 one. Treat it as indicative, not representative.

## Label agreement

No person has labelled any test case yet: the maintainer's blind labels for a 30-case sample aren't in (`eval/kappa/reviewer-labels.json`). Until they are, every label comes from AI models (the agents that wrote the cases and, for the real-world alerts, two other models), so the figures above measure agreement with those models' reading of the labelling rule, not with a person's.

## Limits

- The cases are synthetic. They were written to follow the labelling rule and to include near misses, but real configs are messier, and the figures will be different on them.
- The checks were tuned on a separate dev split (`eval/cases/dev`), written by the same agent that wrote the checks. Its scores aren't reported here, because the checks were fitted to it. The test split was first run once, after tuning; see the history above for what changed after that.
- About 10 risky cases per check is small. The intervals are wide, and a single case moves a figure by several points.
- The labels say whether a setting matches the labelling rule. They don't say whether it's dangerous on a given machine.
- Each case writer labelled mainly the five checks it was given, so a case can be risky for another check without being labelled that way. Those show up below as false alarms or misses and are counted as they stand, without relabelling.
- The checks read config files only. They don't run anything, follow a hook into the script it calls (except scripts in skill, plugin and hooks folders), contact MCP servers, or see settings applied by an administrator outside the files listed in [config-surface.md](config-surface.md).
- Cursor checks cover MCP config and rules files only, because Cursor keeps its run mode in the app, not in a file.
- This is a configuration check, not a security assessment. A clean result doesn't mean a setup is safe.
